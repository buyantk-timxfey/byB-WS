> Статус: черновик плана. Развилки согласованы с заказчиком (см. ниже).
> База: анализ существующей системы byB-WS.

## Согласованные решения (фундамент)

| Развилка | Решение | Следствие для плана |
|----------|---------|---------------------|
| Подход | **Новый стек, рерайт** | Не тащим легаси-код, переносим только бизнес-знание |
| Пользователи | **Один аккаунт, без ролей** | Нет RBAC; платформенный слой проще; аудит — для undo, а не для разграничения |
| Учётное ядро | **Документы + регистры** | Каждая операция = документ; проведение пишет движения в регистры остатков/денег/взаиморасчётов |
| Стек | **Laravel 11 + Inertia + Vue 3 + TS + MySQL** | PHP-экосистема, работает на reg.ru; миграции/ORM/очереди/тесты |
| Хостинг | **reg.ru / ISPmanager (shared)** | Ограничения учтены: сборка локально, очереди по крону |
| Состав модулей | Поставки, Продажи, Склад, Финансы/Банк + **Транспорт + Почта**; **Сделки/CRM, WB, КУДиР — отброшены** | Чистый операционный учёт (ERP/WMS); процесс начинается с Поступления |
| Доставка при закупке | **В себестоимость товара** (распределяем по партии) | Точная FIFO-прибыль по продаже |
| Момент прихода на склад | Поступление проводится при статусе **«В пути»** | «Ожидает» — черновик; «Завершено» — фактически доставлено |
| Касса | **Безналичный «счёт»** | Отдельной логики наличных нет |
| Продажа под заказ | **Разрешена** (склад может уходить в минус) | Себестоимость уточняется при приходе партии |
| Единицы измерения | **Нужны** (шт, литры, упаковки) | Поле ед.изм. у номенклатуры |
| Группы номенклатуры | **Нужны** | Фильтры и аналитика продаж по группам |
| Статьи затрат | **Справочник** | Группировка расходов в P&L |
| Контрагент | **Полные реквизиты + ИНН** | ИНН нужен для авто-сверки выписки |
| НДС | **Без НДС (УСН)**, цены итоговые | Упрощает документы |
| Модель денег | **Statement-first**: деньги строго из выписки + сопоставление | Баланс всегда = банк; P&L кассовым методом |
| Импорт банка | **Только файл 1С** (без API) | Парсер из byB-WS; авто-сверка по ИНН/сумме/дате + ручная доводка |
| Данные | **Чистый старт** | Историю не переносим; вводим начальные остатки вручную |
| Номенклатура | **Справочник товаров** | Аналитика по товарам, нет дублей |
| Себестоимость | **FIFO по партиям** | Точная прибыль по сделке (часто = «конкретная партия») |
| Оплаты | **Авансы + частичные** | Полноценный регистр взаиморасчётов (долги/авансы) |
| Налог/ЗП | **Считаются автоматически** | Производные метрики из введённых данных; ставки в настройках |
| Закрытие периода | **Не делаем** | Один пользователь, доверяем себе |
| Печатные формы | **Не делаем** | Счёт/УПД/акт формируются вне системы |
| Мобильность | **Равный приоритет** | Каждая страница — десктоп и телефон сразу |
| Визуальный стиль | **Обсуждается отдельно** | Дизайн — отдельный детальный раунд |

Девиз продукта: **«1С по надёжности учёта — но по скорости и удобству как современное SaaS»**.

## Часть 1 — Видение и принципы

### Что берём из 1С (сильные стороны)
- **Документ-ориентированность**: всё, что меняет состояние бизнеса, — это документ (поступление, реализация, платёж, списание). Документ можно провести/распровести.
- **Регистры как единственный источник истины**: остатки склада, деньги на счетах, долги контрагентов не хранятся «в полях», а собираются из движений. Любую цифру можно «провалить» до породившего её документа.
- **Перепроведение**: ошибся — поправил документ — перепровёл, регистры пересчитались. Нет ручной правки остатков.
- **Журналы документов** с фильтрами, нумерацией, статусами.
- **Справочники** (номенклатура, контрагенты, счета, статьи затрат) с историей использования.
- **Отчёты строятся из регистров**, а не из «живых» таблиц — отсюда непротиворечивость P&L, склада и взаиморасчётов.

### Что осознанно НЕ берём из 1С
- Толстый клиент и конфигуратор.
- Сложность кастомизации «на все случаи жизни» — у нас один конкретный бизнес.
- Модальный ад, медленные формы, перезагрузки.
- Многопользовательский платформенный обвес (роли, RLS) — у нас один аккаунт.

### Что добавляем сверх 1С (наше преимущество — usability)
- **Скорость**: SPA, оптимистичные апдейты, никаких полных перезагрузок.
- **Поиск по всему** (Cmd/Ctrl+K — командная палитра + глобальный поиск).
- **Клавиатура-first**: создание/проведение документа без мыши.
- **Умные дефолты и автозаполнение** (контрагент, цены из истории, номенклатура).
- **Живые дашборды** из регистров.
- **PWA/мобильность** — у byB-WS это уже сильная сторона, сохраняем и улучшаем.
- **Банк**: импорт выписки 1CClientBankExchange + полуавтоматическая сверка — переносим как ключевую фичу.

### Инварианты системы (правила, которые не нарушаются никогда)
1. Остаток/деньги/долг = СУММА движений соответствующего регистра. Нет «ручного» поля баланса.
2. Движение в регистр пишется ТОЛЬКО при проведении документа (в транзакции).
3. Распроведение/удаление документа удаляет все его движения.
4. Каждое движение ссылается на документ-регистратор (трассируемость).
5. Все деньги — `DECIMAL`. Никаких float в учёте.
6. Проведение идемпотентно: повторное проведение = распроведение + проведение.

### Стек (согласован)

| Слой | Технология | Почему |
|------|-----------|--------|
| Backend | **Laravel 11 (PHP 8.3)** | Остаёмся в PHP-экосистеме (знакомо, работает на reg.ru/ISPmanager); даёт миграции, Eloquent, очереди, валидацию, тесты из коробки |
| Транспорт UI | **Inertia.js** | SPA-ощущение без отдельного REST-слоя и дублирования DTO |
| Frontend | **Vue 3 + Vite + TypeScript** | Реактивные формы документов, компонентность; TS ловит ошибки в учётной логике |
| Стили | **Tailwind CSS** | Быстрая разработка, единый дизайн-токен-слой |
| БД | **MySQL 8** | Проще миграция данных из byB-WS; уже есть на reg.ru |
| Фон. задачи | **Laravel Queue** (database driver, запуск по крону) | Импорт выписок, пересчёт регистров, рассылки |
| Тесты | **Pest/PHPUnit** | То, чего критически не хватало byB-WS |
| PWA | Service Worker + manifest | Переносим подход из byB-WS |

### Ограничения shared-хостинга reg.ru (учтены в плане)
Хостинг — **reg.ru / ISPmanager (shared)**. Отсюда жёсткие следствия для разработки и деплоя:
- **Сборка фронтенда — только локально.** На шаред-хостинге нет Node/`npm run build`. Vite собираем у себя, на сервер льём готовый `public/build`. В git артефакты сборки не коммитим, но в деплой-пакет включаем.
- **Document root → `public/`.** Если нельзя сменить корень сайта в ISPmanager — кладём проект выше корня, а в корне оставляем только содержимое `public/` с поправленными путями к `bootstrap`/`vendor`.
- **Очереди без демонов.** Supervisor недоступен. Очередь гоняем по крону: каждую минуту `php artisan schedule:run`, а в расписании — `queue:work --stop-when-empty`. Тяжёлое (импорт выписки, пересчёт регистров) уходит в очередь, но обрабатывается «пачками» по крону, не воркером-демоном.
- **Composer.** Если на хостинге нет CLI/composer — `composer install --no-dev` делаем локально и заливаем `vendor/` в деплой-пакете.
- **Миграции.** `php artisan migrate --force` через SSH, если SSH есть; иначе — защищённый веб-эндпоинт-раннер миграций (как сейчас `deploy.php`), вызываемый один раз.

> Если в процессе упрёмся в потолок shared-хостинга (крон-очередь слишком медленная для импорта больших выписок, нет SSH) — переезд на VPS остаётся запасным вариантом без смены стека: Laravel переносится 1-в-1.

### Слоистая архитектура

```
UI (Vue/Inertia)
   └─ страницы: журналы документов, формы документов, отчёты, дашборд
App (Laravel controllers + Actions)
   └─ тонкие: валидация ввода → вызов доменного сервиса
Domain (ядро учёта — сердце системы)
   ├─ Document (база): provesti(), otmenitProvedenie()
   ├─ Posting services: формируют движения регистров
   ├─ Registers: AccumulationRegister (остатки), TurnoverRegister (обороты)
   └─ Бизнес-правила (FIFO списание партий, расчёт P&L, налоги, ЗП)
Infra (Eloquent, миграции, импорт 1С-выписки, очереди)
```

### Ядро: документ → проведение → движения

Базовый контракт документа:
```php
interface Postable {
    public function provesti(): void;          // в транзакции: пишет движения
    public function otmenitProvedenie(): void;  // удаляет свои движения
    public function dvizheniya(): array;         // какие регистры затрагивает
}
```
Проведение всегда: `BEGIN → удалить старые движения документа → записать новые → COMMIT`. Это даёт инвариант №6 (идемпотентность) бесплатно.

### Типы регистров
- **Регистр остатков (накопления)**: `+приход / −расход`, остаток = SUM. Примеры: товары на складе (по партиям), деньги на счёте, взаиморасчёты с контрагентом.
- **Регистр оборотов**: только обороты за период, без понятия «остаток». Примеры: доходы, расходы по статьям, объём продаж (для P&L и аналитики).

## Часть 3 — Модель данных: документы и регистры

### 3.1 Справочники (мастер-данные)
| Справочник | Источник в byB-WS | Заметки |
|-----------|-------------------|---------|
| Контрагенты | `counterparties` | **Полные реквизиты**: тип (Поставщик/Покупатель/Оба), ИНН (для авто-сверки выписки), банк. реквизиты, контакты |
| Номенклатура | сейчас строкой в `shipment_items.name` | **Справочник** с ед.изм. (шт/литры/упаковки) и **группой**; нет дублей, есть аналитика |
| Группы номенклатуры | нет | Дерево/список групп для фильтров и аналитики продаж |
| Перевозчики | `carriers` | как есть |
| Счета (деньги) | `bank_accounts` | Касса — это просто безналичный «счёт» (без спец-логики наличных) |
| Статьи затрат | сейчас неявно в `business_expenses` | Справочник для группировки расходов в P&L |
| Склады | нет (один склад) | Один склад по умолчанию; сущность заведена на будущее |

### 3.2 Документы (регистраторы движений)
| Документ | Заменяет в byB-WS | Какие движения формирует при проведении |
|----------|-------------------|------------------------------------------|
| **Поступление товара** | `shipments` + `shipment_items` | Проводится при статусе **«В пути»**: `+Остаток товара` (партия), `+Кредиторка` поставщику, себестоимость = цена + **распределённая доставка** |
| **Реализация (продажа)** | `sales` + `sale_items` | `−Остаток товара` (**FIFO**; допускается минус при продаже под заказ), `+Дебиторка` покупателя, `+Доход`, `+Себестоимость продаж` |
| **Строка выписки** (statement-first) | `bank_operations`/`bank_statement_lines` | `+/−Деньги` на счёт (источник истины по деньгам). При **сопоставлении**: приход↔продажа `−Дебиторка` +Выручка (кассовый доход); расход↔поступление `−Кредиторка`; расход↔статья `+Расход`; перевод — пара строк между счетами |
| **Прочий расход ИП** | `business_expenses` | Начисление `+Расход` по статье; деньги — при сопоставлении строки выписки |
| **Списание/Перемещение** | нет | `−Остаток` (порча/брак) — для точности склада |
| **Выплата ЗП** | `salary` логика | `−Деньги`, `+Расход ЗП` |
| **Ввод начальных остатков** | нет (чистый старт) | Стартовые `+Остаток`, `+Деньги`, `+/−Взаиморасчёты` на дату запуска |

**Особые правила учёта (из ответов):**
- **Распределение доставки**: `carrier_cost` поступления раскидывается на партии товаров пропорционально сумме (цена×кол-во) → входит в FIFO-себестоимость.
- **Продажа под заказ**: если на складе нет партии, остаток уходит в минус, себестоимость берётся плановой/нулевой; при следующем приходе партии — пересчёт себестоимости проданного (или флаг «уточнить»). На форме продажи — предупреждение, но не запрет.
- **Касса** — обычный счёт в регистре денег, безналичный.

### 3.3 Регистры
| Регистр | Тип | Измерения | Ресурсы | Заменяет |
|---------|-----|-----------|---------|----------|
| **Товары на складе** | остатки | склад, номенклатура, партия (документ-поступление) | кол-во, себестоимость | таблица `warehouse` |
| **Денежные средства** | остатки | счёт | сумма | питается **строками выписки** (statement-first); баланс всегда = банк |
| **Взаиморасчёты** | остатки | контрагент, тип(деб/кред) | сумма | **НОВОЕ — в byB-WS нет!** |
| **Доходы/Расходы (P&L)** | обороты | статья, контрагент, период | сумма | расчёт `pnl_detail.php` |
| **Продажи (аналитика)** | обороты | номенклатура, покупатель | кол-во, выручка, прибыль | — |

> **Главный выигрыш над byB-WS**: появляется регистр **взаиморасчётов**. Для торгового посредника «кто кому должен» — критичная цифра, которой сейчас нет как единого источника.

### 3.4 Где будет жить логика финансов
Формула из CLAUDE.md (выручка − закупки − расходы = валовая; налог 16%; ЗП 20% от чистой) переносится в доменный сервис P&L, который читает **регистр оборотов**, а не сканирует «живые» продажи/поставки.

**Кассовый метод (statement-first):** выручка и расходы признаются по факту движения денег — то есть при **сопоставлении строки выписки** с документом (продажей/поступлением/статьёй). Это ровно «выручка = оплаченные продажи» из формулы. Долги (дебиторка/кредиторка) видны отдельно в регистре взаиморасчётов. Деньги в систему попадают строго из выписки → учётный баланс всегда совпадает с банком.

## Часть 4 — Модули по приоритету

Порядок — из CLAUDE.md (критичные → второстепенные).

### Критичные
1. **Финансы / P&L / Банк** (корона)
   - Документы платежей + регистры денег и взаиморасчётов.
   - Импорт выписки 1CClientBankExchange (Windows-1251) — переносим парсер из `api/bank.php`.
   - Полуавтоматическая сверка: строка выписки ↔ документ платежа (логика из `reconcile.js`, 53 КБ — самый сложный перенос).
   - Авто-сопоставление по ИНН/сумме/дате; ручной мэтчинг для остального.
   - P&L: валовая/чистая/налог/ЗП, маржа, ROI, средний чек, динамика 12 мес.
2. **Поставки** → документ «Поступление товара» + регистр склада + кредиторка.
3. **Продажи** → документ «Реализация» + FIFO-списание партий + дебиторка + доход.
4. **Склад** → отчёт «Остатки» из регистра (по партиям, с себестоимостью).

### Второстепенные (по решению переносим только эти)
5. **Транспорт** (топливо/пробег) — прямые таблицы, без регистров (не часть учёта денег/склада).
6. **Почта** — интеграция как есть.
7. Уведомления, push, PWA-офлайн.

> **Сделки/CRM, WB-отчёты и КУДиР — отброшены** (по решению). Процесс в системе начинается сразу с Поступления; поиск товара и заявки ведутся вне системы. КУДиР при желании легко вернуть позже как отчёт поверх регистра доходов/расходов.

> **ЗП** — не отдельный модуль, а вычисляемая метрика P&L (чистая × ставка). Выплата ЗП — это документ «Платёж исходящий» со статьёй «ЗП».

Для каждого модуля в детальной проработке опишем: список документов, движения, экраны (журнал + форма), отчёты, что переносим из старого кода 1-в-1, а что переделываем.

## Часть 5 — UX/UI слой — главное отличие от 1С

### Базовые паттерны
- **Журнал документов**: быстрый список с фильтрами (период, контрагент, статус), inline-статусы, без перезагрузок.
- **Форма документа**: табличная часть с inline-добавлением строк, автоподстановка номенклатуры/цен из истории, проведение по Ctrl+Enter.
- **Командная палитра (Cmd/Ctrl+K)**: переход к любому документу/справочнику/отчёту, быстрые действия («новая продажа», «импорт выписки»).
- **Глобальный поиск** по контрагентам, номенклатуре, номерам документов (перенос идеи `search.php`, но по регистрам/документам).
- **Дашборд** из регистров: деньги по счетам, дебиторка/кредиторка, остатки топ-N, трекер поставок (кольца из текущего дашборда — хорошая находка, сохранить), календарь ETA.

### Печатные формы
По решению **не делаем** — счёт/УПД/акт сверки формируются вне системы. (Архитектурно документ→регистр позже позволяет добавить генерацию PDF без переделок, если понадобится акт сверки.)

### Мобильность (равный приоритет)
PWA сохраняем; каждая страница проектируется и под десктоп, и под телефон сразу. Ключевые мобильные сценарии: посмотреть остатки/долги/деньги, провести оплату, обновить статус поставки. Вход — PIN + WebAuthn/FaceID.

## Часть 6 — Платформенный слой

Даже при одном аккаунте нужны «платформенные» вещи 1С:
- **Нумерация документов** (префикс + сквозной номер по типу и году).
- **Журнал изменений / аудит**: когда, что, старое/новое значение — для отмены ошибок и истории. Лёгкий, без ролей.
- **Импорт/экспорт**: импорт банковской выписки 1С (вход), экспорт в Excel/CSV (отчёты), бэкап/восстановление БД (перенос `db_backup.php`).
- **Справочник настроек**: ставки налога/ЗП (16%/20% по умолчанию, меняются здесь), параметры авто-сверки банка.
- **Аутентификация**: один аккаунт, удобный вход — PIN + WebAuthn/FaceID (перенос из `auth_pin.php`/`webauthn.php`).
- **Ввод начальных остатков**: документ «Ввод остатков» (товары на складе, деньги на счетах, долги контрагентов) — нужен из-за чистого старта.

Роли НЕ делаем, печатных форм и закрытия периода НЕ делаем (по решению). Аудит даёт надёжность без сложности RBAC.

## Часть 7 — Миграция, деплой, дорожная карта

### Старт данных — чистый старт (по решению)
Историю из byB-WS **не переносим**. Стартуем с пустой базы:
1. **Справочники** заполняем вручную (или разовым импортом из старой БД, если удобно): контрагенты (+ ИНН для авто-сверки банка), перевозчики, счета, номенклатура, статьи затрат.
2. **Начальные остатки** вводим документом «Ввод остатков» на дату старта: товары на складе (по партиям с себестоимостью), деньги на счетах, долги контрагентов (дебиторка/кредиторка). Проведение этого документа формирует стартовые движения регистров.
3. Старая byB-WS остаётся **архивом** для справок по истории.

> Плюс чистого старта: не тащим легаси-данные и сразу проверяем, что движок документ→регистр считает остатки/деньги/долги верно.

### Деплой на reg.ru (уход от ZIP-патчей)
- **Сборка локально**: `composer install --no-dev` + `npm run build` (Vite) → готовый пакет.
- **Деплой-пакет** включает `vendor/` и `public/build/` (на хостинге их не собрать). Льём по SFTP/git-pull.
- **Миграции**: `php artisan migrate --force` через SSH; если SSH нет — одноразовый защищённый веб-раннер (наследник `deploy.php`).
- **Очереди по крону**: ISPmanager → Планировщик → ежеминутно `php artisan schedule:run`.
- **Секреты**: `.env` на сервере (вместо `config.local.php`), не в git.
- **Бэкап БД** по крону сохраняем (перенос `db_backup.php`).
- CI: прогон тестов (Pest) перед сборкой пакета — то, чего не было в byB-WS.

### Дорожная карта (фазы)
- **Фаза 0 — Каркас**: стек, аутентификация, layout, справочники (контрагенты, номенклатура, счета, статьи).
- **Фаза 1 — Учётное ядро**: движок документ→проведение→регистры; регистры денег, остатков, взаиморасчётов; базовые отчёты остатков.
- **Фаза 2 — Финансы/Банк (корона)**: платежи, импорт выписки, сверка, P&L. *Раньше остального, т.к. это самый ценный и самый рискованный модуль.*
- **Фаза 3 — Товародвижение**: Поступления (оприход при «В пути», доставка в себестоимость), Реализации (FIFO, продажа под заказ), склад.
- **Фаза 4 — Ввод начальных остатков** и старт реальной работы.
- **Фаза 5 — UX-полировка**: Cmd+K, дашборд, PWA, мобильные экраны.
- **Фаза 6 — Второстепенное**: транспорт, почта.

Порядок фаз 2→3 можно поменять, если важнее сначала закрыть товародвижение.

## Риски
| Риск | Митигация |
|------|-----------|
| Перенос логики сверки банка (`reconcile.js`, 53 КБ) — самый сложный | Переносить отдельной фазой, покрыть тестами на реальных выписках |
| Регистры усложняют разработку vs прямые таблицы | Один аккуратный движок документов окупается на всех модулях; покрыть тестами проведение |
| Ошибки во вводе начальных остатков (чистый старт) | Документ «Ввод остатков» проверяемый и редактируемый; сверка с фактическими остатками/балансами на дату старта |
| Shared-хостинг reg.ru и «новый стек» | Laravel выбран именно ради совместимости; проверить наличие composer/artisan на хостинге заранее |
| Объём рерайта для одного разработчика | Жёсткая приоритизация по фазам; MVP = ядро + финансы |
