# CLAUDE.md — byB-Workspace

## О бизнесе

**byBuka** — торговый посредник. Принимает заявки от крупных юридических лиц, ищет товар у поставщиков, закупает и продаёт.

Основной процесс:
```
Заявка от юр. лица → Поиск товара (вне системы) → Закупка (поставка) → Продажа
```

Система **фиксирует факт** — пользователь вносит данные вручную, система не управляет процессом.

**Пользователей:** 1. Один общий аккаунт, одна роль, полный доступ.

## Приоритет модулей

**Критичные** — здесь всё должно работать безупречно:
- Финансы — полный бухучёт бизнеса, самый важный модуль
- Поставки — трекинг закупок от поставщиков
- Продажи — фиксация сделок с покупателями
- Склад — остатки товара

**Второстепенные** — информационные, не критичны:
- WB — отчёты Wildberries
- КУДиР — книга учёта доходов и расходов
- Мобильная версия

## Логика финансов

Финансы — ключевой модуль, здесь ведётся полный бухучёт бизнеса.

Формула расчёта:
```
Выручка (оплаченные продажи)
- Закупки (ТОЛЬКО завершённые поставки: товары + доставка)
- Расходы ИП (business_expenses)
= Валовая прибыль

Налог    = Валовая × 16%
Чистая   = Валовая − Налог
Зарплата = Чистая × 20%
```

Метрики: маржа, ROI, средний чек, динамика по 12 месяцам.
Интеграция банковских выписок в формате 1CClientBankExchange (Windows-1251).

## Деплой

### Как это работает

Claude редактирует файлы локально → сам собирает ZIP-патч через PowerShell → сохраняет на рабочий стол → пользователь заливает на хостинг.

### Claude собирает патч сам

После внесения изменений Claude запускает Python-скрипт, который упаковывает файлы в ZIP с правильной структурой и сохраняет на рабочий стол:

```
C:\Users\TIMXFEY PC\Desktop\patch-YYYYMMDD-описание.zip
```

Пример имени: `patch-20260608-filter-shipments.zip` — дата + суть изменений, без пробелов.

Корень проекта: `C:\xampp\htdocs\byB-WS`

**Важно:** ZIP собирается через Python (`zipfile`), не через PowerShell `Compress-Archive`. PowerShell создаёт пути с обратными слэшами — сервер (Linux) их не распознаёт и деплоит 0 файлов.

Обязательная структура внутри ZIP:
```
manifest.json
files/
  index.php
  pages/tasks.php
  assets/js/tasks.js
sql/                        ← только если есть SQL-миграции
  001_описание.sql
```

Пути внутри ZIP всегда с прямыми слэшами (`files/pages/tasks.php`, не `files\pages\tasks.php`).

### Патч с SQL-миграцией

Если изменилась схема БД — SQL кладётся в папку `sql/` внутри ZIP. `deploy.php` выполняет все `.sql` файлы из этой папки автоматически при деплое (в алфавитном порядке).

Python-скрипт для сборки патча с SQL:

```python
import zipfile, json, os
from datetime import date

ROOT = r'C:\xampp\htdocs\byB-WS'
DESK = r'C:\Users\TIMXFEY PC\Desktop'
NAME = f'patch-{date.today().strftime("%Y%m%d")}-описание.zip'
OUT  = os.path.join(DESK, NAME)

php_files = ['pages/example.php', 'assets/js/example.js']
sql_files = [('database/migration_005_example.sql', 'sql/005_example.sql')]

manifest = {"version": "1.0", "files": php_files, "sql": [s[1].split('/')[-1] for s in sql_files]}

with zipfile.ZipFile(OUT, 'w', zipfile.ZIP_DEFLATED) as z:
    z.writestr('manifest.json', json.dumps(manifest, ensure_ascii=False, indent=2))
    for rel in php_files:
        z.write(os.path.join(ROOT, rel.replace('/', os.sep)), 'files/' + rel)
    for src, dst in sql_files:
        z.write(os.path.join(ROOT, src.replace('/', os.sep)), dst)
```

### Правила написания SQL-миграций

- **Никогда не писать `USE database_name`** — на хостинге нет прав менять БД, запрос упадёт.
- **Только `CREATE TABLE IF NOT EXISTS`** — идемпотентно, не падает при повторном запуске.
- **Не использовать `ADD COLUMN IF NOT EXISTS`** — не поддерживается MySQL 5.7 на хостинге. Если нужно добавить колонку — выносить в отдельный SQL файл (он может упасть с "Duplicate column" при повторе, это нормально — deploy.php игнорирует коды 1050/1060/1061).
- **Не оборачивать DDL в транзакции** — MySQL делает implicit COMMIT на любой DDL. deploy.php уже исправлен и не использует транзакции для SQL-файлов.
- Нумеровать файлы: `migration_NNN_описание.sql` — deploy.php выполняет в алфавитном порядке.

### Подпись патча

Перед сборкой ZIP написать в чате:

```
Патч 08.06.2026 — Добавлен фильтр по дате в поставках
```

Формат: `Патч ДД.ММ.ГГГГ — <что изменено одной фразой>`. Без эмодзи.

### Что всегда включать в патч при изменении глобальной структуры

Если добавляется новая фича, которая требует изменений в `index.php` (новый HTML-блок, подключение нового CSS/JS файла, новый `<script>` с данными) — **`index.php` обязателен в патче**.

Без `index.php` на хосте не появятся:
- новые HTML-элементы (`#global-searchbar`, `#gs-dropdown` и т.п.)
- подключение нового CSS/JS
- inline-данные для JS (`window._gsData` и т.п.)

Правило: если локально работает, а на хосте нет — первым делом проверить, включён ли `index.php` в патч.

### Что исключается из патча

`build-patch.sh`, `deploy/`, `.git/`, `.env`, `*.log`, `config.local.php`, `CLAUDE.md`, `tools/`, `backups_db/`

## SQL-миграции

**Миграции применяются автоматически через патч** — SQL кладётся в папку `sql/` внутри ZIP, `deploy.php` выполняет их сам при деплое.

### Правильный процесс при изменении схемы БД

1. Обновить `database/schema.sql` (добавить/изменить CREATE TABLE).
2. Создать файл миграции: `database/migration_NNN_описание.sql` (правила написания — см. раздел «Деплой»).
3. Включить SQL-файл в патч через папку `sql/` (Python-скрипт выше).
4. Деплоить как обычно — миграция выполнится автоматически.

**Нельзя** переименовывать или удалять существующие колонки без миграции — это сломает прод.

## Service Worker — важно при добавлении файлов

SW регистрируется как **`sw.php`** — обёртка, которая отдаёт `sw.js`, автоматически подставляя версию кэша из max(mtime) всех JS/CSS/index.php. **Поднимать `APP_VERSION` вручную больше не нужно** — любой изменённый файл инвалидирует кэш сам.

Если добавляется новый CSS или JS файл — по-прежнему **обязательно** добавить его в массив `PRECACHE_ASSETS` в `sw.js`.

## Проверка перед сборкой патча

Перед каждой сборкой ZIP запускать смоук-проверку синтаксиса:

```
powershell -NoProfile -ExecutionPolicy Bypass -File tools\smoke.ps1
```

Прогоняет `php -l` по всем PHP и `node --check` по всем JS. Патч собирается только при «OK: all files passed».

## API-паттерн

Каждый файл в `api/` строго по этому шаблону:

```php
<?php
require_once '../config.php';
session_start();
if (!isset($_SESSION['auth']) || $_SESSION['auth'] !== true) {
    http_response_code(401);
    echo json_encode(['error' => 'Unauthorized']);
    exit;
}
header('Content-Type: application/json');

$method = $_SERVER['REQUEST_METHOD'];
try {
    switch ($method) {
        case 'GET':    /* ... */ break;
        case 'POST':   /* ... */ break;
        case 'PUT':    /* ... */ break;
        case 'DELETE': /* ... */ break;
    }
} catch (Throwable $e) {
    apiError('Ошибка сервера', $e);
}
```

- Проверка сессии — в каждом файле, без исключений.
- DELETE/PUT читают параметры через `$_GET` — это уже сделано в `config.php` (`parse_str`), не дублировать.
- Хелпер `apiError()` из `config.php` — единый способ вернуть ошибку.
- Весь SQL — только через PDO prepare/execute. Никакой конкатенации строк в запросах.

## Трекер поставок на дашборде

Блок под банковскими картами. Показывает все поставки кроме «Завершено», 6 карточек в ряд (каждая = 1/6 ширины `.dashboard-right-bottom` = половина банковской карты).

**Структура карточки:**
```
Вверху:  название контрагента (мелко) + наименование поставки (поле name из таблицы shipments)
Центр:   кольцо Apple Watch (SVG circle, r=36, circumference≈226.19)
Внизу:   дата заказа и ETA
```

**Кольцо Apple Watch:**
- `stroke-dasharray` = circumference, `stroke-dashoffset` = circumference × (1 - pct/100)
- `transform="rotate(-90 50 50)"` — старт с верха
- SVG viewBox="0 0 100 100", ширина 80% карточки, max-width 80px

**Логика цвета кольца:**
| Статус | Цвет | Содержимое центра |
|--------|------|-------------------|
| Ожидает / ⚠️ | Серый `#4b5563` | Текст «Ожидает», вращающаяся дуга-спиннер |
| В пути, прогресс < 50% | Жёлтый `#facc15` | Процент числом |
| В пути, прогресс ≥ 50% | Зелёный `#4ade80` | Процент числом |
| Просрочен (ETA истёк) | Красный `#ef4444` | Пульсирующий крестик (две линии, класс `.tracker-pulse`) |

**Прогресс** = (сегодня − дата заказа) / (ETA − дата заказа) × 100%, максимум 100%.

**Запрос:** берёт `s.name` из таблицы `shipments`.

## Календарь поставок на дашборде

Расположен в `.dashboard-left-col` под блоком просроченных поставок.

**Что показывает:** ETA поставок со статусом «В пути». На днях с ETA — цветная точка (`.cal-dot`). При наведении — тултип с названием поставки и контрагентом.

**PHP-запрос:**
```php
SELECT s.id, COALESCE(s.name,'—') as shipment_name, s.eta,
       COALESCE(c.company_type,'') as company_type,
       COALESCE(c.name,'—') as counterparty
FROM shipments s
LEFT JOIN counterparties c ON c.id = s.counterparty_id
WHERE s.status = 'В пути' AND s.eta IS NOT NULL
ORDER BY s.eta ASC
```
Данные группируются в `$calendarData['YYYY-MM-DD'][]` и передаются в JS через `json_encode`.

**JS:** инлайн в `dashboard.php`. Рендерит сетку 7 колонок, навигация Пн/Пт по месяцам (`cal-prev` / `cal-next`). Тултип позиционируется относительно `.dashboard-calendar`.

**Классы ячеек:** `.cal-day`, `.cal-day--today` (акцентный фон), `.cal-day--has-eta` (кликабельная, с точкой), `.cal-day--empty` (пустышка до первого числа).
